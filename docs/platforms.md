# 适用模型与平台说明

## 1. 能力要求

整书深度研读对模型的要求，按重要性排序：

| 能力 | 为什么需要 | 不足时的后果 |
| --- | --- | --- |
| 文件读写 | 逐章追加写入、断点续写 | 无法产出单文件文档，只能聊天输出 |
| 长上下文（建议 ≥ 64k，最好 ≥ 128k） | 单章全文读取 + 已是长文的分析 | 被迫分段过碎，机制链条断裂 |
| 指令遵循 | 板块编号、标题契约、禁止项 | 格式校验不通过，出现摘要化 |
| 推理能力 | 还原「前提 → 机制 → 结论」链条 | 退化为结论罗列 |
| 中文长文写作 | 输出可读的机制段落 | 段落空转、术语漂移 |

**结论**：优先使用推理型／长上下文模型；小上下文模型仍可用，但必须调小批次并在每章后跑校验。

## 2. 平台矩阵

| 平台 | 使用形态 | 安装/配置 | 备注 |
| --- | --- | --- | --- |
| NotebookLM（Gemini） | ① prompt（逐章） | Configure chat 粘贴 prompt | 原生来源引用；单次回复长度受限 |
| CodeBuddy | ② skill（整书） | `.codebuddy/skills/` 或 `~/.codebuddy/skills/` | 原生 `SKILL.md` 机制，含脚本执行能力 |
| Claude Code / Claude 系列 | ② skill（整书） | `~/.claude/skills/` | 长上下文 + 强指令遵循，整书模式首选之一 |
| Cursor / Windsurf / Cline | ② skill（转规则） | `.cursor/rules/*.mdc`、`AGENTS.md` | 需手动放置为规则文件 |
| ChatGPT（含 Projects / 自定义 GPT） | ② 内容作自定义指令 | Custom instructions / 项目文件 | 无 skills 机制；文件读写能力取决于产品版本 |
| Gemini CLI / 其他 CLI Agent | ② skill（转规则） | `AGENTS.md` | 与代码库同源的规则加载方式 |
| 本地模型（Qwen / GLM / Llama / DeepSeek 等） | ② skill（转规则） | 视推理框架而定 | 需小批次 + 严格的脚本校验 |

## 3. 参数建议

### 3.1 按上下文窗口

| 上下文窗口 | 单次读取原文上限 | `split_book.py --budget` | 每批章节数 |
| --- | --- | --- | --- |
| 32k | ~1.5 万字 | 15000 | 1 章（必要时章内再分段） |
| 64k | ~2.5 万字 | 25000 | 1–2 章 |
| 128k | ~4 万字 | 40000（默认） | 2–3 章 |
| ≥ 200k | ~6 万字 | 60000 | 3–4 章 |

原则：**单章原文 + 已写文档尾部 + 规则文件** 三者之和不要超过窗口的 60%，留出写作用空间。

### 3.2 模型性格与规则适配

| 模型倾向 | 表现 | 对策 |
| --- | --- | --- |
| 过度压缩型 | 喜欢写「总之」「由此可见」 | 明确「禁止概括式收尾」「禁止结论罗列」，并调高 `--min-block-chars` |
| 过度发散型 | 爱补充背景、历史、作者生平 | 强调「禁止书外知识」，让附录 B 承接不确定性 |
| 格式跳脱型 | 标题层级乱用、板块编号跳号 | 必须跑 `check_output.py`，按报错修正 |
| 逐字复述型 | 大段抄原文 | 要求「用自己的语言展开机制，仅在关键定义处逐字引用」 |

## 4. 质量风险与缓解

| 风险 | 检测方式 | 缓解 |
| --- | --- | --- |
| 摘要化 | `check_output.py` 膨胀比 < 1.0 警告；板块字数过短警告 | 回补该章机制展开 |
| 上下文溢出导致后段退化 | 后几章风格明显变短、出现「其余类似」 | 调小 `--budget`，分会话处理，用 `progress.json` 续写 |
| 漏章 | 覆盖率校验（`--manifest`）报缺少章节 | 用 `_骨架.md` 核对章节划分 |
| 术语漂移 | 附录 A 与正文术语写法不一致 | 每批开始前比对术语表 |
| 越界补写 | 正文出现原文没有的推导或数据 | 强制「原文缺口只能标注 `【原文逻辑跳跃】`」 |
| 模态改写 | 弱模态被写成强断言 | 核对 `sifting-rules.md` 的模态保真表 |

## 5. 版本与成本提示

- 一本书完整研读的 token 消耗通常显著高于「一次摘要」：需要读入全文 + 写出长文，属于正常成本
- 长书建议分 2–4 个会话完成，每批结束更新 `deep-reading/_work/progress.json`，避免单会话超限
- 若平台提供「思考/推理」与「快速」两档模型，规则遵循与机制展开用推理档，格式校验与脚本执行不需要高配模型
